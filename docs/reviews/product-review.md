## 2. 评审结论

**结论：有条件通过，允许进入“技术方案设计 + 测试用例设计”；当前不允许直接进入实施开发。**

策划案已经具备可开发 MVP 的主体：目标用户与单局价值明确，核心循环完整，等级、成长、得分、碰撞、刷新和结算规则大部分可配置、可计算、可测试。以下“产品默认决策”视为 V0.1 的补充口径；三方评审需要确认研发可实现、测试可验证，并把确认结果纳入技术方案和测试方案。三方确认完成前，不应开始业务实现。

V0.1 的产品完成定义为：玩家可在微信小游戏目标环境中，从首页进入一局，凭单指相对拖动完成“找水草 → 升级 → 吃低级鱼 → 躲高级鱼 → 死亡或升至 Lv.10 → 结算 → 再来一局”的完整闭环；生命周期、记录保存和适配稳定；不依赖登录、后端、广告或支付。

本评审默认的交付边界是“可导入微信开发者工具、可在约定真机矩阵运行并可提交体验版的完整项目”。实际发布到微信线上仍需要项目主体提供合法 AppID、账号权限、名称/图标及审核材料，不应在缺少这些外部条件时宣称已经上线。

## 5. 产品默认决策

以下决策用于消除 V0.1 歧义。除非三方评审发现明确不可实现或不可测试的问题，技术和测试应直接采用，不再等待额外产品问答。

| ID | 主题 | V0.1 默认决策 |
| --- | --- | --- |
| D01 | 单局起止与计时 | 点击开始、场景初始化完成并把控制权交给玩家时开始“有效游戏时间”；首次用户同时出现教学覆盖层。暂停、切后台和结算表现不计时；死亡以致命碰撞锁定时刻停止，通关以升至 Lv.10 的时刻停止。 |
| D02 | 教学 | `TUTORIAL` 是首次用户叠加在底层 `PLAYING` 上的可玩覆盖层：移动、AI、碰撞、得分、成长、普通野生鱼刷新、连吃和单局计时均照常运行；刷新始终遵守每局开局保护、危险上限和预警。首次吞食或 3 秒后只解除“教程态”，不改变底层玩法运行。开场三条总提示最多展示 3 秒；第一次吃草后隐藏移动/吃草上下文提示；升至 Lv.2 后高亮一条可吃 Lv.1 鱼，第一次吃到低级鱼后隐藏剩余提示并写入“教学完成”。若此前退出或死亡，下局继续教学；记录缺失、清档或损坏时按未完成处理。 |
| D03 | 升级 | `LEVEL_UP` 是 0.3 秒叠加在底层 `PLAYING` 上的表现覆盖层。升级等级在触发时立即生效；移动输入、AI、碰撞、吞食、计分、成长缓存、普通野生鱼刷新、连吃计时和单局计时均继续。升级后的 2 个有效游戏秒内仅禁止新预约 P+2 鱼，其他合法等级仍按刷新约束生成。0.8 秒无敌独立计时，暂停时冻结。 |
| D04 | 同帧与连续升级 | 每个物理帧开始时快照玩家等级和无敌状态；本帧所有关系与危险优先级均按该快照判定。危险成立则本帧不吞食。吞食统一结算后最多升一级；升级表现期间继续获得的成长只累计，不再次触发升级。若 0.3 秒表现完成后溢出仍满足下一等级，在下一逻辑帧再升一级，无需再次吞食，直至不足或 Lv.10。每次实际升级均刷新对应表现和保护，但不得产生重叠表现或重复结算。 |
| D05 | 无敌重叠 | 无敌期间与高级鱼接触不致死、不弹开，可穿过。无敌到期时若同一对碰撞体仍重叠，不追溯判死；该碰撞对须先完全分离，之后再次进入才可致死。 |
| D06 | 可吃鱼最低占比 | 最低数为 `ceil(Target(P) × 50%)`。它是每次刷新决策和“补满后的稳定场面”约束，不是对象离屏瞬间也绝不跌破的零时差承诺。若因离屏等原因跌破，后续每次成功刷新强制选择可吃鱼，直到恢复；位置查找失败可按规则短暂延迟。可食数量只计已经激活且尚未从离场侧完全离屏的可吃鱼；总目标数及危险/P+2/同侧入场配额还必须计入 pending 和正在从出生侧入场的预约对象，避免超发。 |
| D07 | 危险预警时间线 | t=0 通过约束后即预约等级、侧边和位置，并立即占用总数、危险数、P+2 数和同侧入场名额；显示 0.5 秒预警。预警期间实体不移动、不渲染到可见区且碰撞关闭。t=0.5 秒后从完整屏外位置启用运动和碰撞。暂停冻结预警。若玩家升级使其不再危险，激活前重新计算关系并取消红色危险表现。 |
| D08 | 开局保护 | 原文“首局保护”统一解释为“每一局开局保护”：从该局有效游戏时间 0–5 秒，野生鱼候选绝对等级只允许 Lv.1、Lv.2，并继续服从危险上限；不是仅屏蔽动态 P+2。暂停不消耗该窗口。首次安装不另设更强、且不可复现的隐藏难度规则。 |
| D09 | 多指与触摸所有权 | 只有第一个从非 UI 区开始的有效触点拥有移动控制权，直至 end/cancel；其他非 UI 触点忽略且主触点结束后不自动接管。游戏对象不截获触摸，触摸鱼/水草仍属于移动输入。UI 触点独立捕获且优先，可用第二指暂停；从 UI 开始后移出不得转为移动，移出按钮可取消点击；从场景开始后移入 UI 仍是移动且不得触发按钮。普通 `touchcancel` 等同松手并执行 0.2 秒减速；暂停/切后台时直接冻结并清空移动所有权，恢复后必须重新按下。 |
| D10 | 横屏、安全区与 resize | 游戏配置锁定横屏，产品布局支持 4:3–21:9 的横屏逻辑比例，包含平板/折叠屏展开态和左右两个横屏方向；不支持竖屏玩法或多窗口专属布局。布局使用平台返回的安全区域，HUD 顶部带高度取 `max(屏高 8%, 顶部安全 inset)`，所有可碰撞鱼体完整留在活动水域。横屏尺寸/比例变化时自动暂停，按归一化坐标重排并把对象夹回合法边界；不得重置分数、等级或计时。若进入竖屏，冻结玩法并显示旋转提示，回到横屏后由玩家主动继续。 |
| D11 | 暂停退出与记录 | 暂停页“退出”直接回首页并放弃该局，不进入结算、不更新最高分/最高等级/最快通关；“再来一局”会完整清理上一局实体、计时器、连吃、预警、触摸所有权和一次性结果锁。最快通关只由成功升至 Lv.10 的局更新，无记录时显示 `--`。 |
| D12 | 本地存储异常 | 最高记录、教学状态、音效和震动开关使用带 schema 版本的本地数据。最高分/最高等级取 `max`，最快通关只对成功局取未四舍五入毫秒值的 `min`；相同值不重复覆盖。缺失或解析失败时按字段回退默认值，不得阻塞启动；写入失败时本局结果仍正常展示，历史区保持最近一次内存值，可给出非阻断“记录未保存”提示。异常数据不得被当成更高记录。 |
| D13 | 埋点与网络 | V0.1 发布构建不发送任何业务埋点到外部网络；第 13 章事件仅作为可替换事件接口和开发日志字段，用于本地调试/测试报告。任何真实上报、第三方 SDK 或服务端均属于范围变更。 |
| D14 | 鱼尺寸、关系和碰撞 | “相对体积”按线性宽高缩放理解，不按面积。野生鱼默认使用与同等级玩家相同的等级尺寸基准，物种装饰不得改变关系判断；若技术方案保留物种尺寸差，主体宽度偏差不超过 ±5%。碰撞体随主体同步缩放，约为可见主体宽高的 70%，尾鳍/装饰不参与。关系数字与颜色在玩家升级后的下一帧全部刷新。 |
| D15 | 野生鱼交互和安全出生 | V0.1 只有“玩家—野生鱼”和“玩家—水草”参与玩法碰撞；野生鱼之间互不碰撞、互不吞食。初始对象及新危险鱼不得与玩家形成激活后立即接触；技术方案至少保证危险鱼激活后的预测最早碰撞时间不小于 0.8 秒，并保留一个合法躲避方向，否则改位置、改侧或延迟。更严格算法可以替代，但不能降低该产品底线。 |
| D16 | Lv.10 通关 | 升至 Lv.10 的同一时刻锁定通关、停止碰撞和刷新并停止计时；Lv.10 升级闪光可作为 1.2 秒通关表演的开场，不再恢复 `PLAYING`，随后只进入一次通关结算。 |
| D17 | 资源与版权 | 若没有外部美术/音频输入，默认使用随项目生成和保存的原创轻量卡通资源或程序化效果，不从不明来源抓取素材。最终验收不能使用灰盒几何体替代鱼，也不能缺少策划案列出的关键状态、预警、主要音效和图标；资源来源需在项目说明中可追溯。 |
| D18 | 最低运行能力 | 技术方案选择并声明实际最低微信基础库版本；产品不强行依赖非核心新 API。触摸、音频、本地存储和生命周期为必要能力；震动不可用时静默降级为视觉/音频反馈，系统信息或安全区 API 差异必须有回退值。 |
| D19 | 音效与震动默认值 | 首次启动音效与震动默认开启，只有在开始按钮等用户手势后启动音频；开关立即生效并持久化。系统静音、音频启动失败或设备不支持震动时不得影响玩法。 |
| D20 | 文案与语言 | V0.1 仅交付简体中文。玩法关系文案统一使用“可吃 / 同级 / 危险”，结算使用“称霸海域 / 被 Lv.X 鱼吃掉”；同一结果不混用其他术语。 |
| D21 | 初始场景 | 每局生成 6 株水草，其中至少 2 株中心位于玩家中心 1.0–2.5 个玩家主体宽度的环带内且位置合法。可见区初始放置 4 条 Lv.1 中性鱼，鱼体之间不重叠，距玩家碰撞体至少 1.5 个玩家主体宽度；不预放任何致命鱼。玩家获得控制权后，底层 `PLAYING` 刷新器立即照常运行并补向目标数量，包括教程覆盖层仍显示时；所有刷新继续遵守 D06–D08，致命鱼必须从屏外预警入场。 |
| D22 | 随机可复现 | 玩法使用固定逻辑步长；在相同版本、配置、玩法 seed、输入事件及逻辑 dt 序列下，状态和玩法事件日志必须一致。玩法、外观和粒子使用独立随机子流，表现随机不得改变生成与碰撞结果；不要求不同输入采样或不同版本之间产生相同结果。 |
| D23 | 刷新批次与补草 | 一次刷新器逻辑 tick 最多预约/激活 1 条鱼，本版“同一批次”即同一 tick，紧急补充也不得在同一 tick 连发。补草最多尝试 8 个候选点：玩家有有效移动方向时以该方向为中心搜索 ±60°、1.5–3.0 个玩家宽度；静止时使用最后朝向；前方无点则扩展到全圆。仍失败时延迟 0.5 秒，绝不重叠强刷。只有已长成且位于可视活动区的水草算“可见水草”。 |
| D24 | 前后台状态 | `TUTORIAL/PLAYING/LEVEL_UP/PAUSED` 期间进入后台均冻结所有游戏时钟并在返回时停留暂停页；`DEAD/WIN` 已锁定结果后进入后台，返回时直接安全进入对应 `RESULT`，不重演碰撞也不重复结算；`HOME/RESULT` 返回时保持原页面。主动暂停退出按 D11 放弃本局，不弹二次确认。 |
| D25 | 性能门槛 | 目标为 60 FPS。在最低支持真机、目标鱼数和主要特效同时出现时，连续 60 秒平均帧率不得低于 50 FPS、P95 帧间隔不得高于 33.3 ms、不得出现单次超过 200 ms 的玩法卡顿；若最低档设备硬件只能稳定 30 FPS，可在技术方案中预先列为 30 FPS 降级档，但必须平均 ≥30 FPS 且无持续 3 秒低于 25 FPS。代码/本地资源已加载后，从 `onShow` 到首页可交互不超过 3 秒。连续 10 局后，相对首局稳定基线的存活对象和监听器无增长，内存增量不超过 10% 或 20 MB（取更宽者），且无崩溃/黑屏/输入失效。 |

## 6. 产品验收清单

除明确标注“人工体验”的条目外，均应有自动化或可重复的测试证据。最终产品验收以前，研发自测、测试验收和缺陷回归必须全部引用同一配置版本。

### 6.1 启动、首页与单局闭环

- [ ] 冷启动进入首页，无黑屏、报错或依赖登录/网络才能开始核心玩法。
- [ ] 首页展示标题、玩家鱼、开始按钮、最高分、最高等级、最快通关时间、音效和震动开关。
- [ ] 无历史通关时最快通关显示 `--`，不会显示 0 秒或无效值。
- [ ] 点击开始只创建一局；首次用户展示教学，已完成用户直接进入玩法且不重复遮挡。
- [ ] 死亡路径和 Lv.10 通关路径都能各自完整进入一次结算。
- [ ] 结算“再来一局”和“返回首页”可连续使用，不残留上一局对象、得分、计时、连吃、预警或输入状态。

### 6.2 操作与边界

- [ ] 屏幕中除 UI 外任意位置（包括鱼和水草上方）开始拖动都可控制，玩家不跳到手指坐标。
- [ ] 死区、最大半径、速度比例、0.12 秒转向插值、0.2 秒松手减速与配置一致。
- [ ] 到边界只消除法向外速度，切向滑动保留；玩家碰撞体不进入 HUD 或屏外。
- [ ] UI 与移动触摸所有权符合 D09；多指、touchcancel、快速连续按下不会产生幽灵移动或误触。
- [ ] 暂停/切后台会冻结玩法并清空活动触点；恢复后不自动移动、不自动死亡，需玩家主动继续。

### 6.3 食物链、成长与状态

- [ ] Lv.1 只能依靠水草起步，吃满 3 株后升至 Lv.2；水草始终固定 +1 成长、+10 分且不改变连吃。
- [ ] 低等级鱼可吃、同等级鱼弹开、高等级鱼致死；野生鱼之间互不碰撞吞食。
- [ ] 同帧小鱼与大鱼碰撞时危险优先，分数、成长值和吞食数均不增加。
- [ ] 同帧关系使用帧首等级快照；处理顺序不受实体遍历顺序影响。
- [ ] 成长溢出保留且每物理帧最多升一级；跨帧连续升级不会漏掉保护、重复动画或重复结算。
- [ ] 升级时玩法继续，无敌 0.8 秒、P+2 保护 2 秒；重叠到期行为符合 D05。
- [ ] Lv.10 在升级时立即锁定通关，停止计时/碰撞/刷新，只产生一次结果。

### 6.4 生成、公平性与确定性

- [ ] 固定随机种子、固定输入和固定时间步下，鱼等级、侧边、位置、速度和结果可复现。
- [ ] 目标鱼数、基础/加速刷新间隔、危险上限、P+2 上限和每局开局 5 秒保护符合配置。
- [ ] 奇数目标数量的可吃鱼最低数按向上取整；跌破后只用可吃鱼补到目标，位置失败允许按规则延迟。
- [ ] 预警对象从预约起占用所有相关名额，0.5 秒内不移动、不参与碰撞，之后才从完整屏外启用。
- [ ] 每侧最多一条正在预警/入场的致命鱼；两侧均不可用时不得强行生成。
- [ ] 危险出生满足至少 0.8 秒预测最早接触时间和可躲方向底线；没有贴脸、重叠或强制生成。
- [ ] 玩家升级、对象离屏、暂停、死亡清理和对象池复用后，活动计数会重新计算且不会变负、重复或超上限。
- [ ] Lv.1 连续 4 秒无可见可食水草时能在合法安全位置补草；对象在生长期不可食。

### 6.5 得分、连吃、统计与存储

- [ ] 野生鱼成长值、基础分、3 秒连吃窗口、+0.1 步长、×2.0 上限与配置一致。
- [ ] 暂停会冻结连吃窗口；水草不开始、不延长也不打断连吃。
- [ ] 结算的总分、等级、吃鱼数、吃草数、最高连吃和有效生存时间与事件日志一致。
- [ ] 最高分、最高等级只在完成结算的有效单局更新；最快通关只在成功局更新且只保留更快值。
- [ ] 放弃局不更新历史；重启后记录、设置和教学状态仍正确。
- [ ] 空数据、旧 schema、损坏 JSON、超额/写入异常均不会导致崩溃或无法开局。

### 6.6 UI、视觉、音频与可访问识别

- [ ] 不看说明时，玩家能同时凭等级数字、颜色和体型辨认“可吃/同级/危险”，不能只依赖红绿颜色。
- [ ] 等级标记保持屏幕空间可读，不被鱼缩放到不可读；鱼、标记和 HUD 与背景有足够明暗对比。
- [ ] 吃草、吃鱼、连吃、升级、同级碰撞、危险、死亡和通关均有策划要求的关键视觉反馈。
- [ ] 主要音效、环境音和震动开关立即生效并持久化；静音或硬件能力缺失时玩法可继续。
- [ ] 美术不再是灰盒占位；玩家四种状态、至少五种野生鱼基础外观、水草、背景、HUD 图标和关键特效完整。
- [ ] 所有资源来源可追溯，无不明版权素材、外链热加载或与 MVP 无关的广告/支付内容。

### 6.7 兼容性、生命周期与性能

- [ ] 技术/测试文档声明最低微信基础库、DevTools 版本、iOS/Android 系统与真机型号，不以“主流设备”代替矩阵。
- [ ] 至少覆盖 16:9、窄高刘海屏横置比例、不同像素比和平台安全区；HUD 无遮挡，活动区无裁切。
- [ ] 竖屏/旋转/运行中 resize 按 D10 暂停和恢复，单局数据不丢失、对象不跳入非法区域。
- [ ] 来电/切后台/锁屏/音频中断后返回保持暂停，计时、AI、刷新、预警和连吃窗口均未偷跑。
- [ ] 目标为 60 FPS；在技术方案定义的最低档真机上不得持续 3 秒低于 30 FPS，不得出现影响控制的周期性卡顿。
- [ ] 同一真机连续完成或结束 10 局，无崩溃、黑屏、触摸失效、重复结算或明显持续内存增长。
- [ ] 网络断开不会影响已经加载完成的核心单局；无后端/埋点请求失败导致的报错或阻塞。

### 6.8 人工体验验收

- [ ] 至少 10 名未读策划案的首次体验者，在无人额外口头解释下有至少 8 人能在 25 秒内升至 Lv.2。
- [ ] 同一批体验者对至少 20 次死亡进行回述，至少 90% 能指出危险来源；“没看到/来不及且违反出生底线”的死亡必须回查。
- [ ] 首轮观察新手单局是否主要落在 2–5 分钟、首次死亡是否集中在 Lv.3–Lv.5；偏离时先按“公平性 → 成长 → 操作 → 分数”顺序调参。
- [ ] 首次通关率 20%–40% 作为平衡观察项，不在样本不足时伪装成统计结论。

### 6.9 交付与发布准备

- [ ] 仓库包含可复现的安装/构建/运行/测试说明、配置说明、资源来源说明和已知限制。
- [ ] 项目可导入约定版本的微信开发者工具，横屏配置、包体资源路径和发布构建均无调试专用入口泄漏。
- [ ] 发布构建关闭调试面板和外部埋点，但保留测试构建的固定随机种子、碰撞体和刷新计数能力。
- [ ] 测试报告中功能、边界、兼容、性能、生命周期、存储、视觉/音频和回归均有结论；P0/P1 缺陷为 0，已接受的低级别问题有明确说明。
- [ ] 若要求真实发布，AppID、主体权限、名称/图标、隐私/审核材料和发布授权已由项目方提供；否则交付状态只能标为“可提交体验版/待外部发布”。

## 7. 必须澄清项与可采用默认值

### 7.1 技术/测试方案阶段必须给出答案

这些问题可以在方案设计中关闭，不要求现在阻塞方案设计：

1. 技术栈、最低微信基础库、固定时间步与随机数方案，以及测试构建/发布构建的差异。
2. “安全方向”的具体算法、预测碰撞计算、初始安全半径和补草合法位置参数；不得低于 D15 的产品底线。
3. 目标设备、系统、微信版本、屏幕比例和性能采样方法组成的兼容矩阵。
4. 原创美术/音频的生成与落库方式、资源权属记录方式，以及最终构建是否完全本地化。
5. 自动化测试能覆盖的范围、必须使用微信开发者工具/真机验证的范围和证据格式。

### 7.2 无需再问、直接采用的默认值

- 教学计分/计时、升级期间运行内容、无敌重叠：D01–D05。
- 可吃鱼取整与恢复口径、预警时间线、每局开局保护：D06–D08。
- 多指所有权、横屏/安全区/resize、暂停退出与记录：D09–D12。
- 无后端埋点、鱼尺寸/碰撞、安全出生、Lv.10 顺序：D13–D16。
- 原创资源、能力降级、音效/震动默认和简体中文：D17–D20。

### 7.3 只有范围变化时才需要用户/项目方确认

- 是否要求代替项目方执行真实微信发布，而不只是交付可提交的项目；若是，需要另行提供账号、AppID 和明确发布授权。
- 是否启用真实线上埋点或任何第三方 SDK；默认不启用。
- 是否提供品牌美术、商标、商业音频或指定素材；默认使用仓库内原创轻量资源。
